# Research: remote execution for coding agents

Researched 2026-09-24. Scope: how coding agents (Claude Code, Codex CLI, OpenCode) can run application stacks and heavy verification on remote machines instead of the laptop, using primary sources (vendor docs, CLI help, pricing pages) and the tooling already present on this machine and in the target repository. This note records evidence and a proposed pilot; it is not an always-loaded instruction file. Provider names appear here as evidence only. Shared guidance stays provider-neutral, and repository-specific or private infrastructure details live in the private home described under "Private home".

## Problem

The laptop (18 GB, Docker VM capped at 4 GB) cannot run a multi-service dev stack (Node monorepo, Postgres, object storage, headless browser) alongside several agents. The target repository already ships tooling for running several isolated dev instances on one Linux machine, plus scripts for a VPS, so the question is where that machine lives and how work reaches it, not how to orchestrate it.

## What is already on this machine and in the repository

- Installed: Docker via OrbStack (3 CPU, 4 GB cap), `gh` with `gh stack`, `claude`, `codex`, `cursor-agent`, `direnv`, `rsync`, `tmux`, `ssh`. Not installed: `mutagen`, `tailscale`, `hcloud`, `mosh`, `devpod`, `devcontainer`, `opencode`.
- `~/.ssh/config` already has an exe.dev host block with a dedicated key, and the account is on a paid team plan with no VMs. The team's frontend config already allow-lists the exe.dev proxy domain, so at least one teammate uses exe.dev dev boxes.
- The target repository ships two ways to run several isolated dev instances on one Linux host: a per-worktree instance system (port registry, deterministic fast-start script, shared infra containers, per-instance Postgres with snapshots) and an older agent harness (agent IDs 1-5, template-database cloning, JSON verification pipeline, tmux attach) that also includes VPS provisioning scripts for Hetzner with cloud-init, credential sync and Tailscale-only SSH. Both expect Docker, Node and pnpm on the host and nothing else. The VPS README's server prices predate Hetzner's June 2026 change.
- The repository also has a private remote runtime for verifying pushed refs, with browser automation in the guest. It needs a pushed ref, so it complements rather than replaces a dev box. Its details stay in the private home.
- dot-files installs the shell, editor, agent rules, skills and worker roles on any machine with `link.sh`, so a VM can be set up as "a machine" without new tooling.
- The `git-workflow` skill already puts worktrees at `.worktrees/<feature>` and copies `.env*` into them, and both repositories ignore `.local/`.

## Comparison

Criteria from the request: getting uncommitted edits in, caching and startup, persistent services, browser access for human and agents, tests and logs, secrets and private repos, isolation, many branches and agents, reuse, ownership, cleanup, cost, and simplicity.

| Option | Fit | Main tradeoffs |
| --- | --- | --- |
| exe.dev persistent VM (already paid) | Strongest for a dev box. SSH-native so every tool works unchanged; HTTPS preview with team login and no tunnel; `cp` forks a prepared VM; GitHub and LLM credentials never touch the VM; two-second create; Frankfurt region. | Capacity is the plan pool: 4 vCPU/16 GB today, 8/32 for $100/user/month. Shared vCPUs. No idle stop (cost is flat, but idle VMs still occupy the pool until removed). No egress policy. Disk billed on usage; each VM copy counts. Preview ports limited to 3000-9999. |
| Hetzner VM via the repository's VPS scripts | Most raw CPU per euro (dedicated 8/32 at €138/month); scripts exist. | You run the box: Tailscale, patching, credentials, preview URLs need Funnel or Serve, no fork, no HTTPS login proxy. Only worth it if exe.dev's shared CPUs prove too slow. |
| Claude Code cloud sessions | Free with the existing plan; Docker and Postgres available; good for "verify this pushed branch". | Push first; Claude only; one-way handoff; no human-facing app URL; 30 GB disk; per-session. A complement, not a dev box. |
| Private pushed-ref runtime | Best for full-stack verification with a browser on a pushed ref, already integrated. | Needs a pushed ref; not a place to edit. Keep using it; not the subject here. |
| GitHub Codespaces | Mature; idle stop and retention handle cleanup; org billing; 8 cores at $0.72/h. | Requires authoring a dev container for a compose-based repo; copy-only local sync; Claude auth via secrets and reset on rebuild; comparable or higher cost for daily use. |
| Fly.io Sprites | Cheapest disposable per-task sandboxes with MCP and checkpoints. | Auto-pause after 30 s idle kills long test runs unless something holds a connection; Docker unofficial; no Remote-SSH. Revisit for throwaway agent sandboxes later. |
| Daytona, Modal, Ona, Coder, DevPod | Not a fit: per-sandbox cap (Daytona), 24 h lifetime (Modal), opaque pricing plus dev container requirement (Ona), self-hosted platform (Coder), alpha releases (DevPod). | |

Local editing with remote execution versus a fully remote workspace: the fully remote workspace wins for agent work. Edits happen where they run, so "uncommitted changes" is never a transport problem; the repository's 3 GB of `node_modules` and generated files never cross the wire; and two-way sync of a tree that an agent is also editing is exactly what Mutagen and Coder warn about. Local editing stays available two ways without new infrastructure: VS Code or Cursor Remote-SSH (the editor edits the remote tree directly), or a one-way Mutagen replica from a laptop worktree to a VM path that no agent edits. A pushed WIP branch feeds the pushed-ref runtimes.

## Recommendation

Use the existing exe.dev team account as the remote dev box, fully remote, one long-lived VM running the repository's own multi-instance tooling, with agents in tmux and attached from the laptop or phone. Add only three small pieces of glue:

1. A private home for runtime notes and bootstrap scripts, discoverable from any worktree and any tool (below).
2. A bootstrap script for the VM: install Node and pnpm (the base image lacks them), clone through the GitHub integration, run `link.sh`, install dependencies, start shared infra. Stored as the exe.dev default setup script so `new` and `cp` reuse it.
3. A proxy-aware site URL for the app so the exe.dev preview works with cookies and redirects (`SITE_URL`, `TRUST_PROXY`, `SECURE_COOKIES` in the instance env). Verify in the pilot.

Everything else is existing tooling: VM lifecycle by `ssh exe.dev new/cp/ls --json/rm` with tags, human browser access through the login-protected proxy, agent browser access with the Playwright MCP running on the VM against localhost, logs through the repository's instance CLI and PM2, secrets through exe.dev integrations and the repository's existing dev-secrets flow, attach through Claude Remote Control, `opencode attach`, or plain SSH plus tmux.

Cost: nothing new for the pilot. If typecheck and test runs are CPU-bound on 4 shared vCPUs, the decision is Large at $100/user/month (8/32) against a dedicated Hetzner box at €138/month plus operations. Clean-up rule: every VM carries a `task:` tag; `ssh exe.dev ls --json` weekly, `rm` anything whose branch is merged, since idle VMs still occupy the pool and disk.

Not chosen for now: Sprites and Claude cloud sessions are worth a second pilot for disposable, per-task verification once the dev box works, because both remove the "who cleans up" question. A dev container definition would make Codespaces and Ona portable later, but it is not needed for the recommended path.

## Private home

Repository-specific and private runtime details must be discoverable from any worktree and by any agent tool, without living in tracked files or in dot-files. Proposal:

- Location: `<main checkout>/.local/runtime/` in each repository that needs it. `.local/` is already ignored in these repositories and referenced by the `git-workflow` skill. Worktrees live under the main checkout, so any tool resolves it from any worktree with one command: `$(git rev-parse --path-format=absolute --git-common-dir)/../.local/runtime/`.
- Contents: `README.md` (which runtime exists, how to create or reuse an environment, attach, verify, clean up, naming and tags), `bootstrap.sh` (VM setup), and per-provider notes. Nothing here is committed.
- Shared guidance: a short provider-neutral skill in `.ai/skills/` (proposed name `remote-runtime`) that fires before running a dev stack or heavy verification. It tells the agent to look for that directory, follow its notes, prefer reuse over creation, tag what it creates, report the environment identifier, and remove or hand back environments when the task ends. It names no provider.
- Later: the central agent-memory design in the active local spec reserves a per-repository namespace keyed by canonical remote; the runtime notes can move there once that lands. The `.local/runtime/` convention works today and needs no new resolver.

## Pilot

A half-day pilot on the target repository, on the current plan, with no upgrade until measured. Concrete steps and repository-specific values are drafted in that repository's private home, not here.

1. Create one VM sized to the full pool (4 vCPU, 16 GB, 80 GB disk) with the bootstrap setup script and a `task:` tag. Attach the repository's GitHub integration. Nothing else is provisioned.
2. On the VM: `link.sh` from dot-files, clone, install dependencies, start the shared infra and one instance in a worktree.
3. Human check: set the proxy port, open the app at the VM's HTTPS URL from the laptop, log in through exe.dev, confirm login and navigation work with the proxy-aware site URL.
4. Agent check: in tmux, start Claude Code with Remote Control and drive it from claude.ai/code. Task: a small real change in a worktree, run the repository's verification pipeline, take a Playwright screenshot against localhost on the VM, push the branch, open a PR with `gh stack`. Record wall-clock for typecheck, lint, unit tests, and `ssh exe.dev stat` during the run.
5. Concurrency: start a second instance in a second worktree with a second agent (OpenCode via `serve` and `attach`, or Codex over SSH) and rerun step 4 to see contention on 4 vCPUs.
6. Optional: one-way Mutagen from a laptop worktree to a VM path nobody else edits, to confirm the local-edit mode; and one pushed-branch verification through the private runtime and through `claude --cloud` for comparison.
7. Decide: stay on Medium, upgrade to Large, or fall back to the repository's Hetzner scripts. Then write the private `README.md` and `bootstrap.sh` from what actually worked, add the provider-neutral skill to dot-files, and either keep the VM as the long-lived box or `rm` it.

Success: the laptop runs no stack processes during the pilot; the app opens in a browser with no tunnel; an agent completes a change with verification and a PR entirely from the VM; two agents run at once without breaking each other; every created VM is tagged and accounted for at the end.

Known risks: shared vCPUs may make monorepo typechecks slow (measure before judging); disk grows with each VM copy and is billed on usage; team admins can SSH into member VMs (fine for a team account, worth knowing); dev-only secrets in instance env files should keep coming from the repository's secrets flow rather than being pasted into setup scripts.
